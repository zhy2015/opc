# Vision

## 核心命题

在 OpenClaw 中，主会话不应只是一个会答题的 Agent。

它应当被设计成一个**公司级控制中枢**：

- 能理解外部目标
- 能拆出内部组织动作
- 能分配上下文、预算、模型与人力
- 能跟踪子 Agent 状态
- 能在质量、风险、进度之间做管理决策

因此，OPC（One Person Company）的核心思想是：

> **你一个人，就是一个公司；主会话，就是 CEO。**

## 为什么不是普通多 Agent

常见多 Agent 系统的问题：

- 只会“并发多开”
- 缺少清晰角色边界
- 没有正式的审核与返工制度
- 缺少统一任务状态机
- 很难恢复、接管、解释
- 缺少主会话对资源与上下文的精细分配能力

OPC 要解决的，不是“怎么多起几个 Agent”，而是：

- **如何像 CEO 一样管理多个 Agent**
- **如何像公司一样建立部门协作秩序**
- **如何让复杂任务拥有经营上的可控性**

## 设计目标

### 1. 主会话拥有 CEO 能力

主会话负责：

- 接收用户目标
- 做战略判断与任务建单
- 指定由谁来做、用什么模型做、给多少上下文做
- 决定什么时候并行、什么时候审核、什么时候重试、什么时候终止

### 2. 子 Agent 成为“可管理的人力资源”

子 Agent 不是自由聊天实体，而是可管理资源：

- 有角色
- 有职责
- 有权限边界
- 有容量与负载
- 有状态与健康度
- 有产出与考核

### 3. 任务流成为经营流程

复杂任务必须被制度化为：

- 立项
- 规划
- 审核
- 派发
- 执行
- 汇总
- 复核
- 交付
- 归档

### 4. 建立控制面而不只是执行面

真正的多 Agent 管理系统，重点不在 worker 本身，而在 control plane：

- 任务状态
- 资源调度
- 审计留痕
- 恢复点
- 权限矩阵
- 人工接管

## 方法论

OPC 采用四条主线：

1. **组织主线**：CEO → 中层管理 → 执行部门
2. **任务主线**：目标 → 计划 → 执行 → 复核 → 交付
3. **控制主线**：状态机 → 调度 → 监控 → 干预 → 恢复
4. **记忆主线**：上下文裁剪 → 任务台账 → 项目记忆 → 审计归档

## 与 edict 的关系

edict 给出的启发是正确的：

- 分拣
- 规划
- 审核
- 派发
- 执行
- 回奏

OPC 继承其“制度性编排”的思想，但进一步强调：

- 主会话就是 CEO
- 子 Agent 是组织资源而非古风角色扮演
- 管理能力要抽象成 OpenClaw 原生协议与运行时模型

## 结论

OPC 不是一个“多 Agent demo”。

它是一个面向 OpenClaw 的**公司化 Agent 管理框架**：

- 主会话负责经营
- 子 Agent 负责生产
- 控制面负责秩序
- 记忆系统负责沉淀
