# OPC Definition

OPC is the **main-session orchestration pattern** for complex work.
It is not a specific project name, and it is not merely "spawn several agents".

## Core definition

In OPC, the main session acts as:
- orchestrator
- planner
- reviewer
- dispatcher
- monitor
- integrator

Its purpose is to turn complex work into **controlled parallel execution**,
not into free-form multi-agent chatter.

In creative-production work, the control layer must also guard state truth: worker optimism, background jobs, and loose closeout language should not be allowed to silently redefine completion.

## What OPC is trying to solve

OPC exists to solve five recurring problems:
1. the main session should not single-thread every subtask when controlled delegation can help
2. parallel work should not drift into duplicated effort or invisible chaos
3. sub-agents need explicit task boundaries and monitored progress
4. stalled or misdirected work needs intervention, not passive waiting
5. final results must be integrated and delivered cleanly rather than exposing internal fragmentation
6. in creative-production runs, claimed progress and verified progress must remain distinct

## Non-goals

OPC is not:
- a fixed cast of permanent agents
- a roleplay metaphor by itself
- an excuse to parallelize everything
- a replacement for MMM, config ownership, or environment ownership

## Default OPC reflex

Think of OPC as this minimal promise:
- **delegate only when it creates leverage**
- **keep delegated work visible and controllable**
- **intervene when drift appears**
- **integrate before delivery**

If those four things are not happening, it is not a good OPC run no matter how many agents exist.

## Success condition

A good OPC run should produce:
- less main-session bottleneck
- more controlled throughput on complex tasks
- visible sub-task status
- intervention points when work stalls or drifts
- a clean integrated final delivery
